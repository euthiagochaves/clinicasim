VOCÊ É UM GERADOR DE CÓDIGO SÊNIOR. CRIE UM PROJETO COMPLETO CHAMADO “ClinicaSim” COM BACKEND EM .NET 8 (ASP.NET Core Web API) + EF CORE + POSTGRESQL E FRONTEND EM ANGULAR (SPA). O MVP TEM 3 TELAS (INICIAL -> LISTA DE PACIENTES -> ATENDIMENTO). SEM LOGIN.

CONTEXTO / REGRAS DO MVP
- Casos clínicos fictícios pré-carregados via SEED no banco (3 casos).
- Aluno seleciona um caso na lista e inicia um atendimento.
- Ao iniciar, backend cria uma “Session” com um SessionCode curto e aleatório (8 a 10 caracteres alfanuméricos). Esse código será usado futuramente como “código de usuário”, então deve ser curto e amigável.
- O atendimento é baseado em perguntas pré-definidas (A1): o aluno CLICA em perguntas e o “paciente” retorna uma resposta pré-definida do caso.
- Perguntas organizadas por SEÇÃO e CATEGORIA (opção 2):
  - Seções: “Anamnesis” e “Examen Físico”
  - Cada seção tem categorias (ex.: HDA, Alergias, Medicación, etc.)
  - Cada categoria tem perguntas (texto) e cada pergunta tem 1 resposta (texto) no MVP.
- A CADA clique em pergunta:
  - Mostrar no feed/“chat” da UI (pergunta + resposta)
  - Registrar imediatamente no backend um evento de log com timestamp (InteractionEvent)
  - Se clicar repetido na mesma pergunta, registrar repetido (cada clique é um evento novo).
- UI do feed:
  - Não indicar se uma pergunta já foi feita
  - Deve limpar automaticamente após 60 segundos de INATIVIDADE (desde o último clique).
  - Ao limpar, deve sumir tudo sem mensagem, para forçar o aluno a lembrar.
  - Importante: limpar SOMENTE a UI. No backend, o log continua salvo.
- O aluno pode navegar livremente entre seções e repetir perguntas até finalizar.
- “Historia Clínica” (módulo) contém campos obrigatórios preenchidos pelo aluno:
  1) Resumen (obrigatório)
  2) Diagnósticos diferenciales: mínimo 5 itens, ordenados do mais provável ao menos provável (obrigatório)
     - ordenar por drag-and-drop no Angular
  3) Diagnóstico probable (obrigatório)
  4) Conducta (obrigatório) dividido em:
     4a) Estudios sugeridos para confirmar
     4b) Tratamiento si se confirma
- Finalização:
  - Só finaliza se TODOS os obrigatórios acima estiverem ok (incluindo mínimo 5 DDx).
  - Após finalizar, sessão vira SOMENTE LEITURA (bloquear novos eventos e edições).
  - Após finalizar, permitir apenas exportar PDF.
- PDF:
  - Gerado no BACKEND, template fixo.
  - Deve conter: dados do caso, SessionCode, log completo com timestamps, e a história clínica do aluno (resumo, DDx ordenados, dx provável, conduta).
- Professor:
  - Sem painel admin.
  - Acesso por SessionCode: GET PDF via SessionCode.

TAREFA 3 — API: CASOS + SESSÕES (SEM PDF AINDA)
========================
Implemente endpoints REST com DTOs e validação. Mensagens de erro em espanhol.
1) GET /api/cases
   - Retorna lista para triagem: caseId, fullName, chiefComplaint, triage, sex, age
2) POST /api/sessions/start
   - Input: caseId
   - Cria ConsultationSession com SessionCode curto aleatório (8-10 alfanum) e StartedAt
   - Retorna: sessionCode + dados do caso + estrutura (seções/categorias/perguntas) para o front renderizar
3) POST /api/sessions/{sessionCode}/events
   - Input: questionId (ou payload com sectionId/categoryId/questionId)
   - Backend resolve a pergunta e resposta a partir do banco (não confiar no texto vindo do front)
   - Cria InteractionEvent com OccurredAt=UtcNow e salva imediatamente
   - Se sessão estiver Finalized, retornar 409
4) GET /api/sessions/{sessionCode}
   - Retorna status, startedAt/finishedAt e dados básicos (para export e conferência)
5) POST /api/sessions/{sessionCode}/note
   - Salva/atualiza ClinicalNote (rascunho)
6) POST /api/sessions/{sessionCode}/differentials
   - Salva lista ordenada de DDx (rank + text). Substituir a lista inteira em uma operação (simplifica)
7) POST /api/sessions/{sessionCode}/finalize
   - Valida: Summary preenchido, ProbableDiagnosis preenchido, ConductStudies e ConductTreatment preenchidos, e mínimo 5 DDx.
   - Se ok: marcar sessão como Finalized, FinishedAt=UtcNow
   - Depois disso, bloquear novos events/note/differentials (409)

Observação: mantenha o backend como fonte da verdade. Não permita “finalize” sem persistir note e ddx.
